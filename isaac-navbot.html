DEVLOG · 2026.09.24 · OMNIVERSE / ISAAC SIM

Let NavBot
drive through a corridor I built.

After rebuilding the room in Blender, test a robot that settles, drives and is blocked by walls in Isaac Sim. The environment and robot pipelines meet in one physics scene.

01 / TWO PIPELINES

Export the environment through Blender → USD,
import the robot through URDF → USD.

Environment: photos/LiDAR → Blender → USD → Isaac Sim. Robot: the TurtleBot3/NavBot URDF previously prepared for Blender, with completed visual meshes, imported through Isaac Sim's URDF Importer.

Appearance alone does not make a simulated robot. URDF links, joints, mass, inertia, colliders and limits define the dynamics. Preserve these when improving the visual asset.

Previous: corridor USD, cube drop and physics-material bounce test →

02 / ROBOT IMPORT & DRIVE

Verify on flat ground first.
It's not just a visible model.

01 / SETTLE

A free chassis that settles stably

The robot base is free, using imported colliders and joints. First verify stable floor contact. No ROS2, Isaac Lab or navigation policy is enabled in this test scene.

02 / FORWARD

3 seconds forward about 27 cm

Both wheels target 3 rad/s. Flat-ground displacement is about 0.267 m, with 0.33° heading change. Zero wheel speeds and observe settling.

03 / TURN

About 104° left rotation in 3 seconds

Left wheel −2 rad/s, right +2 rad/s: about 104.45° left rotation and 1.5 mm position drift. This checks differential drive, not path tracking.

03 / CORRIDOR PHYSICS

Start on flat ground,
enter the Blender-built environment.

Create navbot_corridor_test.usda, disable the flat-test Ground and use corridor Floor/ Walls colliders. Spawn facing +Y, settle and drive, then separately orient toward the side wall to test blocking.

01 / FLOOR

Floor contact verified

A downward physics raycast hits Floor at Z = 0. After settling, base_link is about 0.010 m high; no floor penetration was observed during this test.

02 / MOTION

About 38 cm of corridor travel

The measurement script recorded about 4.07 seconds, 0.376 m travel and less than 1 mm lateral drift. The video is a separate demonstration run; figures come from the report.

03 / WALL

Wall blocking verified

A side raycast hits Walls at X ≈ 0.248 m. Driving toward +X stops base_link near X ≈ 0.169 m; continued drive causes little displacement, with no observed penetration.

Valid collisions do not establish obstacle avoidance.

The wall physically blocks the robot; no avoidance controller is running. Only one spawn, a short corridor segment and one wall were tested. Whole-room collision coverage and the earlier cube penetration remain unverified.

04 / THE DETOUR

Pressing Play caused a crash.
Failures belong in the record too.

Two user-triggered Play/Run crashes logged usd_usd.dll access errors, which do not identify the root cause alone. A separate script started playback before scene loading and crashed in debug_draw; this timing error is distinct evidence.

Async Rendering

Asynchronous rendering separates drawing and simulation threads. Isaac Sim Full automatically changes related settings between stopped, paused and playing states.

Current workaround

Disable automatic asynchronous switching, then set asyncRendering and asyncRenderingLowLatency to false. Changing only one can be overwritten by the automatic switching logic.

Validation evidence

Five independent Play/Stop cycles passed after the change. Flat-ground and corridor tests also completed without another observed crash.

What remains unproven

Synchronous rendering may avoid the trigger; it does not establish the root cause or a permanent fix. Robot mass, colliders and wheel settings were unchanged.

05 / RECORDING & TIMING

Viewport frame rate
is not the experiment clock.

The first corridor script estimated time from viewport updates and failed the distance criterion. A new top layer also lacked an explicit timeline. Add the range and 60 time codes/s, measure actual simulation time, then retest. Preserve the initial failure instead of lowering the threshold.

The cube test used Windows screen recording; this article captures a selected camera through omni.kit.capture.viewport and omni.videoencoding, then joins and labels clips with FFmpeg. Motion is physics-driven. Capture records it; scripts control drive/stop timing.

Scenes, validation scripts, reports and source video are saved in the project. Restore the spawn pose and zero wheel speeds for the next session.

Download record_corridor.py ↓
How to run it

Save edits, Stop and open the appropriate scene. Load one complete script in Window → Script Editor and Run. The async entry point is included; do not wrap it again or launch competing tests. Use Isaac Sim's Python environment, not system Python.

Keep synchronous-rendering startup settings and a timeline of at least 20 seconds. Derive output paths from the current isaacsim/scenes file. Scripts update reports but do not save USD automatically; other robots need adjusted prim paths, starts and thresholds.

07 / TRY IT IN THE UI

Without a script,
you can still inspect the experiment.

  1. 01
    TIMELINE

    Open the timeline and test scene

    Open Window → Animation → Timeline; enable omni.kit.window.timeline if needed. Learn wheel control on the flat scene first. Stop ends and resets; Pause holds the current state for inspection.

  2. 02
    WHEEL DRIVE

    Set left/right wheel Target Velocity

    In /World/NavBot/Physics, select wheel_left_joint and wheel_right_joint and find angular Drive Target Velocity. This USD field uses deg/s: about 172 on both wheels corresponds to 3 rad/s forward; −115 left and +115 right turns left. Zero both to stop. Keep existing damping/force and check available space first.

  3. 03
    COLLIDER

    Inspect colliders, then contact results

    Enable physics collider visualization in viewport Show. Expand Corridor → Collision, select Floor or Walls and check Collision Enabled. Hiding visuals alone does not reveal hidden collision geometry.

    Let the robot settle and drive slowly. For the separate wall test, Stop, change NavBot Z rotation from 90° to 0°, and drive toward +X. Finish with zero wheel speeds, Stop and restore 90°. No autonomous avoidance runs here.

  4. 04
    MOVIE CAPTURE

    Record from a selected camera

    Open Window → Rendering → Movie Capture, enabling omni.kit.window.movie_capture if needed. Select /World/Camera, Seconds range 0–8, 30 FPS, 1280 × 720, RTX Real-Time 2.0 or Use Current, MP4 output and a new filename. Click Capture Sequence.

    Movie Capture records but does not replay the controller. Zero wheel speed means no motion. Use the script for exact drive-then-stop behavior; Windows screen recording suits menus and interaction demos.
