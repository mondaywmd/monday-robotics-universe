C2: from agent-led experiments to onboard grasp execution

The last update, on October 14, focused on measured layouts, camera alignment and vision-guided grasp simulation. We could calculate how the arm should approach a cube on a computer, but repeatable execution on the real robot still required a great deal of work.

The project has now made tangible progress.

A click on the web panel starts image acquisition, cube localization, path calculation, grasping, lifting, release and return to the observation pose. We have moved the cube to different positions, including left, right and farther targets, and completed multiple real-robot grasps.

The wait has also become much shorter. Early on, it often took about 50 seconds from clicking Start to the arm beginning to move. In the latest three consecutive tests at different, progressively farther positions, my manual timing was consistently around 13 seconds.

The biggest gain, however, is not just a successful grasp or a faster start. I am beginning to understand the whole hardware and software chain, and how the organization of experiments, the placement of computation and the role of an agent affect development efficiency.

I expected application development; we also had to fill gaps underneath

Initially, I expected most of the work to be visual localization and grasp planning: use the manufacturer's robot model and control interfaces, then move the arm along a calculated path.

In practice, many of the foundations also needed checking and additional work.

The supplied URDF model was not completely accurate. Its geometry and camera-to-arm coordinate relationships could not simply be treated as an accurate description of the real machine. We measured, aligned and corrected them until the floor reconstructed from camera data appeared approximately level.

Even after those corrections, servo and mechanical errors remained. A calculated target and the position the gripper actually reached could still differ. That is why we needed repeated tests at different positions, rather than relying on simulation or a single success.

Some supporting modules and software capabilities I had assumed would already be installed and configured were not ready to use. Some needed deployment; others involved drivers, firmware, compilation and flashing. Every low-level update raised questions about compatibility, backups and recovery.

Being able to control the arm from a phone did not mean there was already a reliable programmable trajectory interface. Displayed joint angles were not necessarily measurements of the servos' current positions. We still needed to understand command acceptance, position readback and stopping on faults.

The project consequently reached into areas I had not expected: manufacturer source code, servo protocols, serial data and the controller's receive-and-reply paths. Much of this was reverse engineering—reconstructing how the system worked from code, communication records and observed behavior.

The most stressful experience: flashing a custom control board

Firmware flashing was one of the most memorable and stressful parts of this period.

It was the first time I clearly encountered a situation where the agent did not know how to proceed either. It could read code, analyze protocols and search for information, but there was no generic procedure we could simply apply to this manufacturer-specific board. Online references were limited. How to enter programming mode, which tool to use, how to connect it and how to recover from failure all needed confirmation.

The question was no longer just how to write the code. It was whether we actually understood the hardware in front of us.

We read the manufacturer's source, checked communication and startup behavior, and did substantial reverse engineering. We also contacted the seller remotely to request documents and confirm the procedure, rather than continuing by guesswork.

The seller provided important help: servo APIs, flashing software and tutorials. These device-specific materials filled gaps that general searches and agent analysis could not resolve.

Even with the documentation, the first attempt was tense. Was the compiled firmware correct? Would it affect the original functions? Would the board boot afterward? Could it be recovered if something went wrong? This felt very different from an ordinary software change.

After checking the build configuration, flashing steps and recovery materials, we successfully programmed the firmware. Communication and feedback still needed validation afterward: a successful flash did not mean the entire robot system had been validated.

This exposed a boundary of AI-assisted development. When essential facts belong to a particular device and its manufacturer, an agent cannot invent them. A person still needs to assess risk, contact the supplier, obtain information and decide what to do next.

It also changed my understanding of the scale of the work. We reused the manufacturer's hardware, existing code and open-source tools; we did not build a robot from scratch. But integrating vision, coordinate transforms, planning, collision checking, driver communication, measured feedback and a web interface into a repeatable cube-grasping system was largely our own engineering work.

On the surface, it was just picking up a cube. Underneath was a system spanning application software and low-level hardware.

At first, I did not even know what to ask

The more honest starting point is that I did not know how to formulate many of these questions.

This was my first serious encounter with Raspberry Pi, STM32, drivers and firmware. I lacked the background to know which layer to inspect or which documents to request from the seller. Many terms only began to make sense after I ran into a concrete obstacle.

The project has been learning by doing: encounter something I could not explain, work through it with the agent and documentation, ask the seller more specific questions, then return to the hardware to verify the answer.

Sometimes the biggest step forward was not fixing code. It was finally knowing what to ask.

Gradually, I began distinguishing communication problems from model and execution problems. I also started questioning why the workflow was so complicated, why computation was split between two machines and which operations should become permanent program capabilities.

There is still much to learn, but I am no longer simply waiting for a solution. I can participate in deciding where the project should go next. That has been an important gain.

Stage one: every experiment went through the agent

Initially, almost every experiment was driven by the agent.

Prepare a movement, write or adjust the execution code, check it, deploy it, connect to the robot, run the test and read the logs. If it failed, analyze, fix, verify and deploy again.

The arm might move for only a few seconds, while the whole test cycle took much longer. Different experiments often required newly arranged execution code. Even a small change brought another round of preparation and waiting.

That approach was useful while exploring unfamiliar interfaces. We did not yet know which commands worked, what the feedback meant or where the model differed from the hardware. The agent helped with extensive investigation and experimentation.

But as tests became repetitive, the limitation became clear: the agent was not only helping develop the system; it had become a required step in every experiment.

I could not easily move the cube and immediately try again. Each time, I returned to the conversation and waited for the next operation. The rhythm of experimentation kept breaking. It was slow and frustrating.

Stage two: reusable programs, with the person in control

We began turning repeated operations into reusable programs and built a web control panel.

This changed the way we experimented, rather than merely adding a few buttons.

I could click Start, Stop or Home myself, move the cube and continue testing. The agent gradually stepped out of each execution cycle and focused on development, log analysis and specific problems.

The program ran the established sequence. I chose the conditions and observed the result. A new test no longer required generating a new set of operating instructions.

The benefit was continuity. I could immediately compare positions and notice whether the gripper was too close, too far or biased to one side.

I learned that exploration tools and the running system should gradually separate. Repeatedly verified operations should become capabilities of the program itself.

Stage three: a workflow split between Windows and the robot

The web panel made experiments easier, but the internal workflow was still distributed.

Some image processing, localization, path analysis and collision validation depended on the Windows environment, while the robot handled acquisition and hardware execution. Tasks required data transfers, result waits and state handoffs between the PC and Raspberry Pi.

The PC had more computing power, but computation alone did not determine the wait before a grasp. Image transfer, Wi-Fi, service discovery, process startup and state synchronization all added time.

Failures were harder to interpret too. Had the image stopped updating? Was the network slow? Was calculation unfinished? Or had the robot not received the result?

We spent a lot of time investigating and adjusting waiting conditions and timeouts. Having part of the workflow on Windows and part on the robot made startup, deployment and use awkward.

Looking back, we were often treating symptoms of the cross-machine workflow. Waiting longer could not remove the boundaries the task had to cross.

Not every fault was caused by Wi-Fi. Serial backlog, image reception and state interpretation had their own causes. But the distributed setup made diagnosis harder and slowed development.

Stage four: persistent computation onboard the robot

We eventually decided to move the computation required for grasping onto the robot and reuse persistent processes wherever practical.

This was a turning point.

Acquisition, localization, planning, collision validation and execution could now connect locally. The web page mainly triggered tasks and displayed results. The robot no longer depended on Windows to calculate every grasp.

The Raspberry Pi had not suddenly become faster than the PC. Instead, data generation, computation and execution were closer together, with fewer transfers, handoffs and environments to coordinate.

Persistent processes reduced repeated initialization, model loading and connection waits. The system began to behave like a robot capable of carrying out a task, rather than an experimental setup with half its workflow on each machine.

This was the qualitative improvement I felt: after a click, the task could follow a fixed workflow. Experiments finally became continuous.

From moving the arm to completing a grasp

The motions themselves evolved alongside the architecture.

Coordinate transforms, gripper opening and closing, forward reach and contact height all needed hardware checks. A mathematically valid target did not automatically produce a useful grasp.

Manual operation provided valuable references: how to unfold the arm, turn toward a target, choose which joints participate in the approach and position the gripper before closing.

Early tests included floor contact, grasps too far forward or back, and release before the cube had been lifted high enough. Some came from localization or mechanical error; others were simply actions the plan had specified incorrectly for the intended task.

The sequence became explicit: approach, descend, close, lift by about 30 cm, release and return to the observation pose.

A forward, partly unfolded intermediate pose—pose B—made the approach more direct. After closing, the arm could retract inward and select a suitable pitch instead of following an unnecessarily rigid lift directly above the target.

These adjustments retained joint limits and collision checks while reducing unnecessary motion constraints. Tests at left, right, near and far positions then helped refine the actual grasp alignment.

Measured feedback, and a task that can finish cleanly

Hardware testing taught me to distinguish three things:

  • A command has been sent or its execution sequence has finished.
  • The joints have reached their target positions.
  • The cube has actually been grasped.

We added measured servo position readback, used actual joint angles as the planning start and checked arrival after execution. Whether the cube is securely held still involves onsite observation.

This also improved the start-state logic. A small deviation after homing should not automatically prevent the next task merely because the arm is not exactly at an ideal pose. Planning from the measured position and checking the resulting path is more useful.

The intended workflow is straightforward:

Power on → click Start → acquire this round's images → localize and plan → execute the sequence → save the result and finish.

The task cleans up its state afterward. The next click triggers fresh acquisition and planning, without automatic retries. The web panel distinguishes execution completion, unconfirmed arrival and failure instead of hiding them behind a generic success message.

Why the first attempt could work and the second fail

Repeated use exposed problems that a single success could hide.

RGB sometimes kept updating while depth stopped. In other cases, the first attempt succeeded and later queries repeatedly timed out.

For stalled depth, we traced publication, DDS delivery and callback scheduling, investigated fragment reassembly and adjusted the persistent depth subscription's reliability configuration.

For query timeouts, we inspected the host driver and controller reply paths, identified a serial receive backlog and changed reception to bounded batch reads to reduce its impact on new replies.

Health reporting also needed to distinguish computation from loss of responsiveness. Busy did not mean failed, but it could not justify waiting indefinitely either. We separated busy, idle and failed states while retaining the existing communication deadlines and fault handling.

These changes were less visible than a successful grasp, but they mattered for completing the second and third attempts.

Our own design took wrong turns too

The difficulties did not all come from hardware or manufacturer interfaces.

As debugging continued, we accumulated checks and patches. Some made sense individually but became redundant or contradictory together, blocking tasks the robot could otherwise perform.

Examples included repeatedly demanding fresh transform timestamps during a stationary observation, applying overlapping admission checks after acquiring the round's image, and using inconsistent criteria for home verification and the next starting pose.

We reviewed the whole workflow, removed redundant checks and clarified state meanings, organizing a task into observation, planning, execution and cleanup.

Collision checking, joint limits, STOP, watchdogs and communication deadlines remained. The aim was to remove duplicate procedures and restrictions that did not usefully distinguish real risks.

This also prompted a reflection on AI collaboration. An agent can keep analyzing and patching the immediate problem, but resolving local issues one by one does not ensure that the overall workflow makes sense.

Sometimes I need to stop and ask whether we are fixing a specific defect or maintaining an unsuitable workflow with more and more patches.

I need to stay involved in those higher-level decisions. Delegating code does not mean handing over the entire project direction.

From 50 seconds to 13: measure first, then reduce overhead

Once the task was working, waiting became the most obvious usability problem.

It was tempting to blame planning and collision checking. But separate measurements showed that solving alone could not explain the whole delay. Initialization, model loading, service discovery, per-point calls, image localization and communication were all accumulating time.

We reused persistent computation, reduced repeated startup and connections, moved collision validation to batched in-process execution and reused the image-localization runtime. Each round still processes a newly acquired image rather than reusing the previous target.

For the current defined grasping scenario, the production path was simplified to IK, interpolated trajectories and standalone FCL collision checks. It no longer needs to start MoveIt, although the installation remains available for future, more complex obstacle avoidance.

Removing MoveIt from this execution path did not remove collision validation. The robot model still needs loading, and the final execution trajectory still needs checking.

After these changes, the latest three consecutive tests at different, progressively farther positions each took about 13 seconds from clicking Start to the arm beginning to move—roughly 74% less waiting than the earlier observation of about 50 seconds.

These are onsite manual timings, not a controlled benchmark or the duration of the entire grasp. The gain comes from architectural changes and subsequent optimizations together, not a single modification.

The improvement in actual use is nevertheless clear.

Two unfamiliar boards, and a whole chain of learning

This was my first deep encounter with a Raspberry Pi 5 and an STM32-based OpenRF4 control board.

More importantly, I started understanding the relationships between these subjects.

Data received does not mean a callback has executed. A command sent does not mean the arm has arrived. A check passing on a computer does not guarantee reliable hardware operation.

Those distinctions became meaningful through actual failures and investigation.

Decisions I would make earlier next time

If I started again, I would separate exploration from routine execution earlier.

An agent can help investigate unfamiliar interfaces. Once a procedure becomes repetitive, I would turn it into a reusable program and give the person a direct test interface, instead of rewriting execution code for each attempt.

I would also decide where computation belongs earlier, considering data sources and task needs. A task the robot must perform independently should, where practical, run onboard. Cross-machine computation should have a clear benefit that accounts for transfer and synchronization costs.

When similar timeouts and state problems recur, changing thresholds is not enough. I need to inspect how work is divided, how many boundaries the task crosses and where initialization or admission checks are repeated.

For information gaps around custom hardware, I would ask the manufacturer for precise documentation sooner. An agent can help interpret and analyze it, but cannot replace device documentation, measurements or human risk judgment.

This was my first project of this kind, and there were many detours. The lessons about experimentation, hardware communication and architecture will outlast any particular patch.

Where the project stands

Within the current test setup, the robot can perform vision-guided grasps at multiple positions from a web trigger and proceed to another round. The latest three onsite tests each had a start delay of about 13 seconds.

This is not yet a complete autonomous litter-collection system. Long-term success rates, positioning errors and reachability still need measurement. Driving toward a target, placing objects in a collection container and continuous autonomous operation have not all been integrated.

The priority now is to stabilize this version and test it on more real tasks, rather than immediately adding features.

The way the project operates has changed too: from an agent intervening in every small experiment, to a person running consecutive tests, to onboard computation and execution.

It was much harder than expected, with frustrating and stressful moments. But cubes are now being picked up repeatedly, and the wait has fallen from about 50 seconds to about 13.

An equally important gain is that I have moved from not knowing how to ask questions toward understanding problems, asking better questions and participating in engineering decisions.

I have learned a great deal from this experience.
