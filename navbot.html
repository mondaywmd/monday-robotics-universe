CASE FILE 001 · NAVBOT

From hitting a pillar
to learning a detour.

A hands-on robot-learning project grew into an experimental system with reproducible scenes, behavior cloning, PPO, safety layers, mirror protocols and OOD diagnostics.

00 / MY ROBOT TRAINING DESK

Start with the six interfaces I use throughout this project.

This is not fully automatic robot training. I set direction, acceptance criteria and evidence standards; the agent shortens implementation cycles. Gazebo reveals behavior and TensorBoard reveals optimization.

01 · WINDOWS / CHATGPT

02 · WSL / UBUNTU

Where training actually runs

ROS, Gazebo, Python, source code and training run in Ubuntu. Each run preserves configuration, checkpoints, CSVs and TensorBoard events.

03 · GAZEBO / NAVBOT

Inspect what the robot actually did

Gazebo turns scenes, sensors and actions into observable behavior: straight-line drift, pillar collisions, hesitation and mirrored-route consistency.

04 · CODEX AGENT

Turn a specification into code and experiments

The Codex agent works in the same WSL project to edit code, run smoke tests and collect evidence. I judge whether results are credible and what to change next.

05 · TRAIN / REPLAY / REVIEW

Run training, then review behavior

Start with smoke tests, then 1k, 5k, 10k and 20k budgets. Freeze the policy for baseline, mirrored, random-obstacle and OOD evaluations. Recordings use 4× playback to compare paths and failures.

06 · TENSORBOARD

Look at the data, but don't be fooled by the curve.

Track success, collisions, timeouts, return, episode length, KL, clip fraction, actor/critic loss and parameter updates. Stable curves cannot replace Gazebo behavior validation.

These six interfaces form a repeatable Vibe Robotics loop: Question → specification → agent implementation → Gazebo run → video and TensorBoard evidence → human judgment for the next iteration.

00 / WHY THIS PROJECT

More than getting from A to B.

The goal is to complete the learning loop firsthand: observations, policy actions, rewards, trajectory collection, PPO updates and frozen evaluation of what the robot actually learned.

My background is Houdini, VFX, procedural simulation, USD and production pipelines. NavBot connects digital-world building and debugging to observations, actions, rewards, policies, rollouts and evaluation. A mobile robot makes sensing, wheel behavior and collisions directly inspectable.

01 / THE LOOP

Understand the learning loop first.

Gazebo scene → LiDAR + goal →Policy→ Linear / angular velocity →Reward→PPO Update
The original experimental hypothesis.

The base rule controller only moves toward the goal. PPO does not own all navigation; it supplies small Δv and Δω . Keep corrections near zero in clear space, slow and turn around obstacles, then return control to the goal controller.

Why this design?

If the rule controller already avoids all obstacles, PPO's contribution is obscured. Restricting it to goal seeking makes learned sensor-based avoidance testable.

02 / TWO EXPERIMENT LINES

One task, two approaches.

LINE A · RESIDUAL LEARNING

Keep the goal-tracking controller and let PPO learn obstacle-avoidance corrections.

  • 16D observation; bounded velocity corrections
  • Start with a fixed single column, then gradually add disturbance and OOD.
  • Investigate failure mechanisms, mirror bias and safety limits

LINE B · CLEAN START

Start from random weights with temporal LiDAR and a strictly mirrored actor.

  • 78D observation: current LiDAR, change rates, action history and goal geometry
  • Online random scenes with 1–5 pillars and feasible-path checks
  • Start with behavior cloning, then use PPO for harder failures

04 / STARTING OVER

The most important iteration was a complete redesign.

Early on, a successful one-sided route led straight into RL, without mirrored driving data or frozen acceptance criteria. Each failure prompted more rewards, conditions and geometric rules, making the system harder to explain.

THE FIRST PHYSICS LESSON

Trying to speed up training, I drove too fast.

An early experiment raised the cruise command to about 0.80 m/s . The robot looked faster, but training data deteriorated. Straight-line calibration in an empty scene showed that at 0.30 m/s , lateral drift and heading error were unacceptable. The command was reduced and frozen at 0.25 m/s , repeated testing would achieve a level of stability that could be used for training.

0.80m/s Outside the credible range
0.30m/s Unacceptable straight-line drift
0.25m/s Conservative validation value used here

ROBOTIS specifies about 0.22 m/s maximum translation for TurtleBot3 Burger. This test does not isolate real actuator limitations: drive, friction, slip, frequency, acceleration and model behavior may all contribute. Commands beyond a credible physics envelope make RL learn simulator artifacts rather than the intended task.

EARLY ROUTE · WHAT WENT WRONG

One-sided success was mistaken for a sound learning foundation.

  1. Establish one feasible route to the goal
  2. No paired left/right mirror data
  3. Hand control to RL and expect it to fix the behavior automatically
  4. Keep adding rewards, conditions and path algorithms after unexpected results
  5. The system is becoming more complex and the reasons for failure are becoming more and more difficult to tell.
REBUILD · DATA BEFORE OPTIMIZATION

Validate the task and data pipeline before introducing learning.

  1. Redesign the controller and scene generation
  2. Generate a left/right mirrored pair for every base route
  3. Verify success with 1, 2, 3, 4 and 5 pillars before adding RL
  4. Freeze successful trajectories, seeds, scene-validity rules and safety thresholds
  5. BC pretraining, frozen-policy inference, then PPO fine-tuning

06 / BUILD LOG

This project is more than a rising curve.

Ask a falsifiable question at each step before advancing to the next stage.

  1. 01
    CONTROL BASELINE

    First, protect a truly functional baseline.

    After restart, obstacle-free Direct Goal with heading compensation achieved 10/10 success, 0 collisions, 0 timeouts and 71.5 mean steps. Freeze and preserve this baseline.

  2. 02
    FIXED FAILURE

    Make the failure unambiguous: the baseline must hit the central pillar

    Start (0,0), pillar (1,0), goal (2,0). Pure goal seeking follows the centerline and terminates below 0.20 m LiDAR range. This makes failure inevitable and PPO's task explicit.

  3. 03
    RESIDUAL PPO V1–V3

    A working action interface does not mean learned avoidance

    Bound residual actions to ±0.05 m/s and ±0.30 rad/s; zero residual exactly reproduces baseline. After 5k steps, the first checkpoint still scores 0/10 with 10/10 collisions. Manual control establishes a feasible turn, but the learned correction is too weak.

  4. 04
    BEHAVIOR CLONING + PPO

    Give the strategy an anchor for a successful action first.

    Three expert trajectories yielded 648 samples; BC achieved 3/3 in Gazebo. BC-initialized PPO collected 5,299 steps with 24/24 training successes, then scored 10/10 in fixed-scene evaluation.

  5. 05
    HELD-OUT & CURRICULUM

    Fixed-scene success does not establish generalization

    V4 scored 59/60 across six unseen small-perturbation scenes. V5's lateral-pillar curriculum kept 59/60 while moving the failure from pillar-right to yaw-left; overall reliability did not improve.

  6. 06
    ADVERSARIAL OOD

    A harder test exposes the limits

    Twelve permanent OOD tasks, five deterministic runs each: V5 achieved 43/60, with 11 collisions and 6 timeouts. Its 71.67% score shows that 98.33% under small perturbations is not broad generalization.

  7. 07
    MIRROR CONSISTENCY V7

    More symmetrical output, worse robots.

    Mirror loss fell from 3.20 to 0.19, but permanent OOD success dropped to 38.33% and collisions rose to 48.33%. Symmetry was not enough: correct safe-action anchors and strict paired trajectories were missing.

  8. 08
    V8 + CLEAN START

    Rebuild around successful mirrored trajectories

    V8 collected 24 successful mirror pairs, 48 episodes and 5,617 16D samples. The later clean-start version uses dense 360° LiDAR and 78D temporal inputs, trained from random weights rather than the old actor.

08 / WHAT I LEARNED

The difficult part is defining the evidence.

01

Training success ≠ generalization

Report fixed scenes, small perturbations and adversarial OOD separately. Held-out 59/60 and OOD 43/60 are both valid results for different tests.

02

Failure requires a trajectory, not just a label.

A timeout may mean no progress or overshooting near the goal. Per-step goal angle, velocity, gate state and LiDAR distinguish these mechanisms.

03

Symmetric constraints require the right action anchor

Making the output more consistent, on the right and on the left, is not automatically safer. Without a pair of success tracks, symmetrical losses may even damage the otherwise useful side.

04

Simulation infrastructure is also the subject of research.

Cached targets, leftover pillars across processes and gzclient/gzserver disagreements can corrupt training signals. Reset protocols and server-side checks are part of the experiment.

09 / LIMITS

What the evidence does not establish.

  • No real-robot or sim-to-real validation.
  • Barriers remain mainly static cylinders, without complex shapes and dynamic pedestrians.
  • The intended 0.40 m clearance was not consistently maintained.
  • Final evaluation used fresh non-OOD scenes; it was not permanent OOD certification.
  • 10k PPO steps remain a small budget; the same mirrored five-pillar safety failure remains unresolved.

10 / WHERE IT GOES NEXT

Connect the learning loop to the wider robotics portfolio.

NavBot / Gazebo→ Procedural scenes →OpenUSD→Isaac Sim→Domain Randomization→Sim-to-Real

Before extending training, investigate repeated safety failures. Then connect procedural Houdini/Blender worlds, USD assets, sensors and batch evaluation into one inspectable pipeline. Agents help build assets; humans remain responsible for protocols and conclusions.
