10 月 14 日，上一次更新的重点还是布局测量、相机对齐和视觉引导抓取仿真。当时，我们已经能在电脑里计算机械臂如何接近方块，但距离真机反复完成任务，还有很多工作。

现在，项目终于有了实质性进展。

通过网页点击开始，机器人可以获取图像、定位方块、计算路径，执行抓取、抬升、松爪和归位。我们把方块移到不同位置，测试左右偏移和更远的目标，已经完成了多轮真机抓取。

等待时间也明显缩短了。早期从点击到机械臂开始运动，往往需要约 50 秒；最近连续三次不同位置、逐渐更远的目标测试，现场人工计时都在 13 秒左右。

但这一阶段最大的收获，不只是抓取成功和速度提升。更重要的是，我开始理解整条软硬件链路，也逐渐认识到：项目怎样组织实验、计算放在哪里、哪些工作应该交给 Agent，都会直接影响开发效率。

原以为是应用开发，实际还要补齐底层能力

最初，我以为主要工作会是视觉定位和抓取规划：使用厂家提供的机器人模型和控制接口，让机械臂按照计算出的路径运动。

实际做下来，才发现很多基础条件也需要自己验证和补齐。

厂家提供的 URDF 机器人模型并不完全准确。模型中的几何关系，以及相机与机械臂之间的坐标关系，不能直接当作真机的准确描述。我们做了实测、对齐和修正，才让相机重建出来的地面基本呈现为水平。

即使坐标关系调整好了，舵机和机械结构本身仍然存在误差。计算得到的目标位置，与夹爪真正到达的位置之间，依然可能有偏差。这也是为什么必须在不同位置反复测试，不能只看仿真结果，或者成功一次就认为问题已经解决。

另外，我原本以为设备已经具备的配套模块和软件能力，并没有全部安装、配置好。有些需要自己部署，有些涉及驱动、固件、编译和刷机。每次底层更新，还要考虑版本是否兼容、备份是否完整，以及失败后能不能恢复。

手机能够控制机械臂，不代表程序已经拥有可靠的轨迹执行接口；系统能够显示关节角度，也不代表那些数值就是舵机此刻的实测位置。程序要完成任务，还需要弄清楚命令怎样被接收、实际位置怎样读取，以及异常时如何停止。

项目因此深入到了最初没有预料的地方：阅读厂家源码、核对舵机协议、分析串口数据、追踪下位机接收与应答路径。很多工作带有逆向分析的性质，需要从代码、通信记录和实际行为中，一点点还原系统怎样运行。

最有压力的一次经历：给定制控制板刷固件

刷固件是这段时间让我印象最深、压力也最大的一段经历。

这是我第一次明确遇到：Agent 也不知道该怎么继续。它可以阅读代码、分析协议、查找资料，但面对这块厂家定制的控制板，没有一套能够直接照搬的通用操作流程。网上可用的参考有限，怎样进入烧录模式、使用什么工具、怎样连接，以及失败后如何恢复，都需要进一步确认。

这时候，问题已经不只是代码怎么写，而是我们是否真正了解手里的硬件。

为了继续推进，我们需要阅读厂家源码，核对通信协议和启动流程，做不少逆向分析。同时，也需要与商家远程沟通，索取资料、确认操作方法，不能只靠猜测试下去。

商家在这个阶段提供了关键帮助，包括舵机相关的 API、烧录软件和操作教程。这些针对实际设备的资料，补上了通用搜索和 Agent 分析无法解决的信息缺口。

但即使拿到了资料，第一次操作仍然很紧张。编译出来的固件是否正确？会不会影响原来的功能？刷完能不能启动？如果失败，还能不能恢复？这些问题带来的压力，与普通软件修改完全不同。

我们检查编译配置、烧录步骤和恢复材料，最终完成了固件烧录。之后还要继续验证通信和反馈，因为烧录成功并不代表整个机器人系统已经通过验证。

这段经历让我认识到 AI 辅助开发的一个边界：当关键信息掌握在特定设备和厂家手里时，Agent 无法凭空补齐事实。仍然需要人去判断风险、联系供应商、获取资料，并决定下一步怎么做。

它也改变了我对工程量的理解。我们复用了厂家硬件、已有代码和开源工具，并不是从零制造机器人；但把视觉、坐标转换、规划、碰撞检查、驱动通信、实际反馈和网页操作组合成一套能够反复使用的抓方块系统，基本上是我们自己完成的工程集成与开发。

表面上只是抓起一个方块，背后却是一套跨越上层软件和底层硬件的系统。

最开始，我甚至不知道该怎样提问

更真实的情况是，最开始我连这些问题应该怎样问，都不清楚。

第一次接触树莓派、STM32、驱动和固件时，我缺乏足够的背景知识。遇到问题，不知道应该检查哪一层，也不知道向商家索取什么资料。很多术语都是在实际遇到障碍之后，才开始理解的。

这个项目一直是在边学边做：先遇到一个无法解释的现象，借助 Agent 和资料逐步理解，再带着更具体的问题与商家确认，最后回到设备上验证。

有时候，最大的进展还不是修好了代码，而是终于知道应该问什么。

慢慢地，我开始能够区分通信问题、模型问题和执行问题，也开始主动质疑流程为什么这么复杂、计算为什么要分散在两台机器上，以及哪些事情应该交给固定程序完成。

我仍然有很多需要学习的地方，但已经不再只是等待一个解决方案，而是能够参与判断下一步应该怎么走。这是这一阶段非常重要的收获。

第一阶段：每个实验都要经过 Agent

最开始，实验几乎全部由 Agent 推动。

准备一组动作，编写或调整执行代码，检查、部署，连接机器人，再运行测试、读取日志。如果失败，就继续分析、修复、验证，然后重新部署。

机械臂实际运动可能只需要几秒钟，整个测试周期却很长。不同实验还经常需要重新组织执行代码。一个小改动，也会带来一轮准备和等待。

探索未知接口时，这种方式有价值。我们还不知道哪些命令有效、反馈代表什么，以及模型与硬件有哪些差异，Agent 帮助完成了大量调查和试验。

但随着测试开始重复，问题越来越明显：Agent 不仅在帮助开发，也成了每轮实验必须经过的环节。

我很难连续改变方块位置，然后马上再试一次。每次都要回到对话里，等待下一轮操作，实验节奏被不断打断。这个阶段非常慢，也相当痛苦。

第二阶段：把重复实验交给程序，把控制权交给人

后来，我们开始把重复操作整理成固定程序，并做了网页控制板。

这不只是增加几个按钮，而是改变了实验方式。

我可以自己点击开始、停止或归位，换一个方块位置后继续测试。Agent 逐渐退出每一轮执行，转而负责开发、分析日志和处理明确的问题。

程序负责执行既定流程，人负责选择实验条件和观察结果。每次测试不再需要重新生成一套操作步骤。

由此带来的提升，不只是操作更方便，而是终于能够连续做实验。不同位置的效果可以立即比较，夹爪偏前、偏后或者偏向一侧，也更容易发现。

这一阶段让我认识到：探索工具和运行系统应该逐渐分开。已经反复验证的操作，应当变成程序本身的能力。

第三阶段：流程分布在 Windows 和机器人两端

有了网页，实验方便了，但系统内部仍然比较分散。

当时，部分图像处理、定位、路径分析和碰撞验证依赖 Windows 上的环境，机器人负责采集和硬件执行。整个任务需要在电脑与树莓派之间传递数据、等待结果、交接状态。

Windows 的计算能力更强，但一次抓取的等待并不只由计算速度决定。图像传输、Wi-Fi 连接、服务发现、进程启动和状态同步，都会增加时间。

出了问题，也更难判断：是图像没有更新、网络传输慢、计算没完成，还是机器人没有收到结果？

我们花了不少时间排查和调整各种等待条件与超时期限。部分流程在 Windows，部分在机器人本机，也让启动、部署和使用都不够顺畅。

回头看，很多时候我们是在处理跨机流程带来的症状。延长等待，并不能消除流程本身需要跨越的那些边界。

当然，不能把所有故障都归因于 Wi-Fi。后来确认的串口积压、图像接收和状态判断问题，都有各自的原因。但分散的运行方式，确实增加了排查难度，也拖慢了项目推进。

第四阶段：迁到机器人本机常驻运行

后来，我们决定把抓取所需的计算迁到机器人本机，并尽量复用常驻进程。

这是一次关键转折。

图像获取、定位、规划、碰撞验收和执行可以在机器人本机衔接，网页主要负责触发任务和显示结果。机器人不再需要依赖 Windows 完成每一轮计算。

它的价值并不是树莓派突然比电脑算得快了，而是数据产生、计算和执行更靠近，减少了跨机传输和交接，也减少了运行时需要协调的环境。

常驻复用进一步减少了重复初始化、模型加载和连接等待。系统开始更像一台能够独立完成任务的机器人，而不是电脑和机器人各运行一半、每次都需要重新配合的实验装置。

这也是我感受到的质的飞跃：点击之后，任务可以沿着固定流程继续，实验终于变得连贯。

从“机械臂会动”到“完成一次抓取”

架构逐渐清晰的同时，动作本身也经历了很多调整。

坐标转换、夹爪开合、前伸距离和接触高度，都需要通过真机核对。一个计算上正确的目标，并不自动意味着夹爪会以合适的姿态抓住方块。

现场手动操作提供了很有价值的参考：机械臂怎样展开、怎样转向目标、哪些关节参与接近，以及夹爪在哪里闭合更合适。

早期测试出现过触地、夹持位置偏前或偏后，以及还没抬高就松爪等现象。有些来自定位和机械误差，有些则是计划本身就安排了不符合预期的动作。

我们逐渐将流程明确为：接近目标、下降、闭爪、抬升约 30 厘米，然后松爪并归位。

进入抓取前，采用向前半展开的 B 中间姿态，使接近动作更直接。闭爪后的抬升则允许向内回收，并选择合适的俯仰姿态，不再要求以过于固定的姿态沿目标正上方运动。

这些调整保留了关节限制和碰撞检查，同时减少不必要的动作约束。随后，再通过左右和远近位置测试，修正实际夹持偏差。

建立真实反馈，也让任务能够正常结束

真机调试让我逐渐理解，以下三件事不能混为一谈：

  • 指令已经发送或执行完成。
  • 关节已经到达目标位置。
  • 方块已经被成功抓住。

我们接入舵机实际位置读取，用实测角度作为规划起点，并在动作结束后检查到位情况。方块是否真正夹稳，目前仍结合现场观察确认。

这也帮助我们修正了起点逻辑。归位存在少量偏差时，不应仅因为没有精确回到某个理想姿态，就拒绝下一轮任务。更合理的方式是从当前真实角度规划，并检查新的路径。

最终希望实现的操作流程很直接：

开机 → 点击开始 → 获取本轮图像 → 定位与规划 → 执行整组动作 → 保存结果并结束。

任务结束后清理状态，下一次点击重新采集和规划，不自动重试。网页则明确区分执行完成、到位未确认和任务失败，避免用一个笼统的“成功”掩盖实际状态。

为什么第一轮成功，第二轮仍可能失败

单次成功之后，连续使用暴露了更多问题。

我们遇到过 RGB 仍在更新、Depth 却停住，也遇到过第一轮成功、后续查询持续超时。

针对深度图停更，我们沿发布、DDS 接收和回调调度路径取证，检查分片重组与交付情况，并调整了常驻 Depth 订阅的可靠性配置。

针对查询超时，我们检查主机驱动和下位机应答路径，确认过主机串口接收积压，随后改为有界批量读取，减少积压对新查询回复的影响。

健康状态判断也需要区分正常计算与失去响应。程序正在忙碌，并不等于已经失效；但忙碌也不能成为无限等待的理由。因此，我们明确了忙碌、空闲和失败状态，保留原有通信期限与故障处理。

这些工作不如一次抓取成功那么直观，却决定了系统能否继续完成第二轮、第三轮任务。

我们自己的设计，也走过弯路

困难并不全部来自硬件或厂家接口。

随着调试推进，我们不断增加检查和补丁。有些检查单独看有理由，叠加后却出现重复和矛盾，让本来可以执行的任务被软件条件阻断。

例如，静止观察期间反复要求坐标变换时间戳刷新；已经获取本轮图像，还要经过另一套重复准入；归位验收与下一轮起点检查采用不同标准。

我们后来重新梳理完整流程，减少重复检查，统一状态含义，把一次任务明确分成观察、规划、执行和收尾。

必要的碰撞检查、关节限制、STOP、看门狗和通信期限仍然保留。需要减少的是重复流程，以及不能有效帮助判断真实风险的限制。

这里也有一个关于 AI 协作的反思：Agent 很擅长围绕眼前问题继续分析和修补，但局部问题逐个解决，并不保证整个系统的组织方式合理。

有时需要停下来问：现在是在修一个具体缺陷，还是在用越来越多的补丁维持一个不合适的工作方式？

这种高层判断，我需要自己持续参与，不能因为代码交给 Agent，就把项目方向也完全交出去。

从 50 秒到 13 秒：先测清楚，再减少开销

功能逐渐跑通后，等待时间成为最明显的体验问题。

最初很容易认为是规划和碰撞检查太慢。但分项测量表明，求解本身无法解释全部等待。初始化、模型加载、服务发现、逐点调用、图像定位和通信，都在累积时间。

我们逐步复用常驻计算环境，减少重复启动与连接，将碰撞验收改为批量、进程内执行，并复用图像定位所需的运行环境。每轮仍然处理新采集的图像，不沿用上一轮目标。

针对当前明确的抓取场景，生产流程进一步简化为 IK 求解、插值轨迹和独立 FCL 碰撞检查。当前运行不再需要启动 MoveIt，但保留安装，方便以后扩展复杂绕障。

不用 MoveIt，不等于取消碰撞验收。机器人模型仍然需要加载，最终执行轨迹仍然需要检查。

经过这些调整，最近连续三次不同位置、逐渐更远的目标测试，从点击到机械臂开始运动都约为 13 秒。与早期约 50 秒相比，等待时间减少约 74%。

这是现场人工计时的阶段性结果，不是严格受控的性能基准，也不是整组抓取的完成时间。改善来自架构调整与后续优化共同作用，不能全部归功于某一项修改。

但从实际使用体验看，变化已经非常明显。

第一次接触两块板，学到了一整条链路

这是我第一次深入接触树莓派 5 和基于 STM32 的 OpenRF4 控制板。

最初关注的只是机械臂怎样抓到方块，后来却沿着整个系统学了很多以前没有接触过的内容：

领域实际接触到的知识
上位机与下位机树莓派与 STM32 的分工，计算、控制和反馈如何衔接
串口与协议字节流、数据帧、请求应答、解析、缓冲区和接收积压
ROS 2节点、话题、服务、回调，以及 Executor 如何调度执行
DDS 与传输发布订阅、QoS、可靠传输、图像分片与重组
驱动与固件主机驱动和下位机固件的区别，沿源码追踪指令和应答

更重要的是，我开始理解这些知识之间的关系。

数据已经收到，不等于回调已经执行；命令已经发送，不等于机械臂已经到位；电脑上验证通过，也不等于真机运行一定可靠。

这些认识，都来自实际遇到问题之后的排查。

下一次，我会更早做哪些决定

回头看，如果重新开始，我会更早划清探索与运行之间的边界。

未知接口可以通过 Agent 辅助调查和实验；一旦流程开始重复，就尽快整理为固定程序，让人直接掌握测试入口，而不是每次重新编写执行代码。

计算部署也应该更早结合数据来源和任务需求决定。机器人需要独立完成的流程，应尽量具备本机运行能力；跨机计算则应建立在明确收益之上，同时考虑传输与同步成本。

当同一类超时和状态问题反复出现时，也不能只继续调整阈值。需要检查工作怎样分配、流程跨越了多少边界，以及是否存在重复初始化和重复准入。

遇到定制硬件的信息缺口，则应该更早向厂家索取准确资料，而不是让推测代替确认。Agent 可以帮助理解和分析，但不能替代设备文档、实测证据和人的风险判断。

这是第一次做这类项目，确实走了很多弯路。但这些关于实验方式、硬件沟通和架构选择的经验，比某一个具体补丁更有长期价值。

当前的成果，以及下一步

目前可以确认的是：在现有测试场景中，机器人已经能够由网页触发，在多个位置完成视觉引导抓取，并继续进行下一轮任务。最近三次现场测试的启动等待都约为 13 秒。

这还不是完整的自主垃圾回收系统。长期成功率、定位偏差和可达范围仍需积累；移动底盘接近目标、投放到回收容器，以及自主连续作业，也尚未全部串起来。

接下来，优先事项是稳住当前版本，用更多真实任务检验它，而不是立即增加更多功能。

这一阶段，从每个小实验都需要 Agent 介入，到人能够连续点击测试，再到机器人本机独立完成计算和执行，项目的推进方式本身也发生了变化。

过程比想象中困难得多，有不少令人头痛、甚至有压力的时刻。但现在，方块确实被一次次抓起来了，等待从约 50 秒缩短到了约 13 秒。

而另一项同样重要的收获，是我从最初不知道怎样提问，逐渐走到了能够理解问题、提出问题，并参与作出工程决策。

这段经历，确实受益匪浅。
